# Audit checklist for existing CLAUDE.md files

This is the rubric the skill uses when a `CLAUDE.md` already exists. The job is **not** to diff against the raw template — an existing file will have been customized, reordered, and grown project-specific sections. The job is to judge whether each *recommendation below* is satisfied, and to surface only the gaps.

A recommendation is satisfied when its **intent** is met, even if the wording differs from the template. Don't flag a section just because it's phrased differently — flag it only when the intent is missing, weakened, or stale.

## How to classify each item

For every rubric item below, classify the existing file as one of:

- **OK** — intent is present and current. Not a finding; don't mention it.
- **Missing** — the recommendation is absent entirely.
- **Outdated** — present, but reflects an older convention than the current recommendation (see the "Outdated looks like" notes — these are the high-value finds).
- **Stale** — present, but references something that no longer exists (a deleted subtree, a renamed doc, a leftover `<placeholder>`).

Each finding gets one line: the file, the item, the classification, and a few words of *why it matters* so the user can decide. Keep it scannable.

A leftover unfilled placeholder (`<like this>`) anywhere in an existing file is always a **Stale** finding — it means a previous scaffold run was never completed.

## Root `CLAUDE.md` rubric

Source of truth: `templates/CLAUDE-root.md`.

### R1 — "Always read first" block
Mandates reading `@docs/CONCEPT.md` and `@docs/ARCHITECTURE.md` before any work, using `@`-references so they load at session start — **plus** the changelog read that no `@`-reference can express: `ls docs/changelog` for the **full** index (not a tail), the newest 10 entry files in full **as a floor rather than a fixed measure** — the dated filenames let a session see whether ten entries is two days or one, and extend when it's thin — and a `grep -rli` over the folder for the area about to be touched, stated as numbered actions and tolerant of an absent folder. Optionally, between the window and the grep, a **delegated digest**: a cheap subagent reads the entries behind the window and returns ~20 lines, never persisted.
- *Why:* anchors every session in the contract docs, and makes the whole changelog reachable without any shared summary file. The steps are a **set**, not alternatives: at real velocity the window is only two or three days deep, the full index is the only thing that *names* what is older, and the grep is the only thing that opens it. Bound the index to a tail below the template's ~1000-entry crossover and distant history stops being nameable; drop the grep and it stops being readable. There is deliberately no curated file carrying the reach instead — see R1's migration.
- *On the optional delegated digest:* its **absence is not a finding** — OK, not Missing. It costs a subagent call at session start and buys nothing in a repo whose window already covers everything, so whether it earns its keep is the owner's call, not the rubric's. What **is** a finding is a version of it that **writes its output to a file**: that is the committed digest returning in disguise, with every contention property back and staleness added on top, since a persisted generated summary is wrong the moment the next entry lands. Rewrite the step to be ephemeral, and route the file it produced to R1's migration below. Also flag a digest step **pointed at the main session rather than a subagent** — it then costs the context it exists to save — and one that asks for a *summary of what changed* rather than the fixed class (rejected alternatives, things tried and removed, constraints that still bind, reversals), which reproduces the diff-recap failure R3 guards against, one level up.
- *Outdated looks like:* **`@docs/CHANGELOG-DIGEST.md`, or any curated digest / decision-log file, in required reading** — the retired reach mechanism, and a file every change appends to and every compaction rewrites, which is the collision the per-entry folder exists to remove; route it to R1's migration below rather than just dropping the reference. **`@docs/CHANGELOG.md` still in required reading on a migrated repo** — the migration removes that file, so the reference dangles and the session starts with a broken load and no changelog at all; **the index bounded to a tail on a folder small enough to list whole** (`ls docs/changelog | tail -40`), which silently caps reach at the window and is exactly what the digest used to paper over — but a tail is *correct* past the template's ~1000-entry crossover, where the full listing costs more than it returns and the full brief moves to the delegated subagent, so check the folder's size before calling this a finding; **no grep step**, leaving the agent holding a list of names it was never told to open; **the window stated as a hard count with no date check** — ten entries is one day in a busy repo and a month in a quiet one, so a bare count silently means something different in every project it's copied into; the window **described without a bound** ("read the recent changelog"), or omitted entirely; the steps present but written as prose rather than numbered actions, which is how they come to be read as optional; plain links instead of `@`-references; worded as optional ("you may want to read") rather than a hard "always read".

#### R1's migration — a repo carrying a `docs/CHANGELOG-DIGEST.md`

An earlier version of this skill scaffolded a digest, so a repo can hold one with everything else about it current. Removing it is a **conversion, not a delete**: every line in it was earned by a change somebody judged load-bearing, and for some of those lines the digest is the only place that judgement is written down.

**Detect the file, not the reference** — `test -f docs/CHANGELOG-DIGEST.md`, run once per audit regardless of what any `CLAUDE.md` says. Keying the finding off the `@`-reference misses the case that matters most: a digest whose reference someone already removed by hand is a file every milestone still gets appended to by habit and no session ever loads, which is strictly worse than one that is at least read. The reference and the file are two independent facts and all four combinations occur:

- **Both present** — the ordinary case. Run the steps below.
- **File present, reference gone** — orphan. Same steps, minus the R1 half of step 6; report it as an orphan so the user knows why a file they thought was retired is being touched.
- **Reference present, file gone** — nothing to fold. Don't run the steps: just drop the reference and the R3 digest rule. This is a dangling `@`-reference, so it is also breaking session start today.
- **Neither** — nothing to do, not a finding.

It is cheap — a digest is ~100 lines by construction — so this runs inline in the audit session. No fan-out.

1. **Resolve every line to its entry.** Each line should name a slug in `docs/changelog/`. Open that entry.
2. **Fold in whatever the entry doesn't already say.** If the line only restates what the entry's lead and detail already carry, drop it: it was a pointer, and the index does that job now. If it carries something the entry doesn't — usually the *significance*, "this is the decision that settled X" — append it to that entry's `## Detail` under a uniform marker — `Significance (from the retired digest): …`. The marker matters: without it, "which entries were milestone-grade" stops being recoverable as a set, and that grouping is real information somebody curated. With it, `grep -rl 'from the retired digest' docs/changelog/` returns exactly the old digest's membership. This is the one sanctioned edit to a landed entry, allowed because it adds to the record at its existing address rather than moving it — so **show the fold-and-drop plan and get confirmation before touching any entry**; step 6d's show-the-diff rule covers `CLAUDE.md` edits only.
3. **Report every line that doesn't resolve, and delete nothing while any remain.** A line naming no slug, or a slug with no file, is content with no home — the user decides whether it becomes its own dated entry or is dropped. Never discard one silently.
4. **Delete `docs/CHANGELOG-DIGEST.md`**, in the same commit as the folds, once every line is folded or accounted for.
5. **Write the migration's own changelog entry.** One file per change applies to this change too, and the entry is the only dated, greppable record of the event as opposed to the rule: how many digest lines were folded, into which entries, and how many resolved to nothing. The `CLAUDE.md` edits in step 6 change the standing rule; they do not record what happened.
6. **Re-point required reading (R1) and strip the digest rule from *Changelog discipline* (R3) in the same change.** A digest rule pointing at a deleted file, or required reading loading one, is worse than leaving both in place. **Sweep the subtree `CLAUDE.md` files too** — S1–S5 carry no required-reading item, so a hand-written subtree file that repeats the orienting reads is the one place a digest reference survives an audit that only ever looked at root.

**The mid-flight case.** A branch or worktree open across the conversion carries a `CLAUDE.md` that still mandates digest appends, so its merge hits a **modify/delete conflict** on `docs/CHANGELOG-DIGEST.md`. Resolve it by folding the branch's new lines into the entries they name and **keeping the delete** — the resolving session's instinct is to restore the file, which silently undoes the conversion. The conflict is loud, so nothing is lost either way, but say it anyway: this is the same hazard R3's migration carries its own mid-flight section for.

### R2 — Source-of-truth statement
States that CONCEPT/ARCHITECTURE are the source of truth for *what* and *how*, and that contradictions in code should be flagged rather than guessed past.
- *Why:* forces doc/code reconciliation instead of silent drift.
- *Outdated looks like:* absent, or softened so the agent isn't told to flag contradictions.

### R3 — Changelog discipline
Every change recorded in `docs/changelog/` as **its own file**, named `YYYY-MM-DD-<slug>.md`. No single changelog file and no entry numbers — one file per change is what makes two parallel changes unable to collide, since no two can reach for the same path. The entry is **two tiers**: a bounded **lead** (1–5 lines, ~20 words per line, never one packed run-on line) written as durable project memory — what is now *true that wasn't before*, plus the *why* in a clause when it isn't obvious, not a recap of the diff — and a **detail** section **owed whenever one of these exists and omitted only when none does** — an alternative rejected, a constraint that still binds, a known limit or deferred follow-up, a gap a future session would otherwise assume the verification covered — which **never restates the lead**, bounded by *purpose* plus a ~40-line ceiling. Also present: that a landed entry file is **never renamed, moved, or deleted**, because its path is its address, and that a change revisiting or reversing an earlier entry's decision **cites that entry's slug**, so rationale reaches back past the recent window without any entry growing; that the entry is written as part of the same change, one file per change, none skipped; that **where `HEAD` is doesn't matter** — branch, worktree and `main` all write the file the same way, with nothing staged or moved at any point; and the **findability rule** — with no digest and no curated decision list, an entry is reachable only by its slug in the index and by grep over the folder, so the slug names the thing rather than the activity (`expired-refresh-tokens`, not `auth-fixes`), and a decision that must not be re-litigated is stated in the words someone would search for rather than alluded to.
- *Why:* durable project memory the agent can rely on at a bounded read cost. The bound comes from the **window times the detail ceiling** — the newest 10 are read in full, both tiers — not from the lead, and not from the index, which is unbounded but costs one filename per entry; what the lead's bound buys is orientation speed and something an index line and a back-citation can point at. The detail is **owed rather than optional** because a rejected alternative exists only in the session that rejected it, so unrecorded there it is unrecoverable from the diff, the code or the log; and it never restates the lead because the measured failure of an unbounded-by-length section is padding, not omission. And the addressing scheme has to be unable to break silently. Findability carries what the digest used to: once no file is guaranteed to be read past the window, the slug and the entry's own wording are the whole reach, which is why they are a rule rather than a style note.
- *Outdated looks like:*
  - **frames the content as "summarize what changed"** with no notion of state-delta / why / not-from-the-diff — produces low-value diff recaps. Layout-independent: this find applies whatever scheme the file is on.
  - **frames brevity only as "one line" / "as short as possible"** with no per-line bound — gameable, since the model then packs everything onto one long line — instead of bounding it (1–5 lines, ~20 words/line). Also layout-independent.
  - **a bounded lead over an unbounded detail section**, or no purpose test on the detail at all. The file grows without limit and the ceiling never bites. Note this is the *inverse* of the old failure: entries that sprawl are now expected to carry a bounded lead, not to be truncated.
  - **no immutability rule** for landed entry files. The file states the folder convention but never says the path is the address, so a tidy-up rename breaks every citation with nothing to catch it. This is the successor to "never reuse or reorder numbers" and is the piece most easily dropped when migrating.
  - **a fragment-and-fold section** — entries staged in `docs/changelog.d/<slug>.md` and folded into a single file at landing, with an empty-on-`main` invariant, a janitor rule, or a residual-renumber case. That is the retired staging area, and it was only ever necessary because the destination was one file: you staged because a number claimed on a branch went stale, and you folded because there was one file to fold into. A permanent per-entry folder removes the reason for it, so the fold now has nothing to fold. Route this to the migration below rather than patching the section.
  - **a digest rule** — a milestone or must-not-re-litigate decision also earning one to three lines in `docs/CHANGELOG-DIGEST.md`. That is the retired reach mechanism: one file every change appends to and every ~100-line compaction rewrites, reintroducing in miniature exactly the collision the per-entry folder removes. The compaction is the worse half — an append conflicts trivially and resolves by keeping both sides, but rewriting the older half is a real semantic conflict, and it falls due precisely when the project is busy enough to have parallel work in flight. Route it to R1's migration: the rule and the file go together.
  - **a numbering, append-to-the-end, or archive rule** — monotonically increasing integers, never reorder, phase-completion moves to `docs/CHANGELOG-archive.md`, numbers globally unique across both files. Same migration. Do **not** treat the numbering rule's mere presence as the finding on a repo the migration rubric below classifies OK.

#### R3's migration — a repo still on the single-file changelog

**Classify before offering.** A repo on the retired scheme is not automatically Outdated. The convention changing is not a deprecation notice, and a young repo must not be pushed through a migration for its own sake.

- **OK, not a finding** — no `docs/CHANGELOG-archive.md`, no duplicate entry numbers, `docs/CHANGELOG.md` under ~400 lines, and commits land direct-to-`main` with worktrees not in use. Mention the folder convention once in the run summary as available on request; don't raise it as a gap.
- **Outdated** on any one of: **`docs/CHANGELOG-archive.md` exists** — an archival pass has already happened, so the toil is recurring rather than hypothetical; **duplicate entry numbers exist** (`grep -hoE '^[0-9]+\.' docs/CHANGELOG.md docs/CHANGELOG-archive.md 2>/dev/null | sort | uniq -d`, across both files, since a cross-file duplicate is the same defect); **`docs/CHANGELOG.md` is past ~400 lines**; or **the repo commits via Branch+PR (R6), or worktrees are in use per the a2 answer (R6b)**. Word that last trigger as the *answer*, never as the worktree subsection's presence: a file with no subsection whose owner answers *yes* is textually absent and semantically yes, and two auditors would otherwise classify it differently. Parallel landings make the numbering invariant unenforceable at any size — there is no global sequencer, so two same-day sessions can claim the same number and merge cleanly.

**A repo that audits OK on layout can still have an orthogonal R3 finding** — brevity framed as "as short as possible", or no state-delta framing. Apply those fixes **inside the file's existing convention**, preserving its numbering, append-to-the-end and archive wording verbatim. *Applying updates*' generic "rewrite that section to the current recommendation's intent" would otherwise pull the whole layout in behind a brevity fix, migrating a repo this rubric has just said should keep its single file.

**The migration is one item spanning R1, R3, R6/R6b and the backfill — offer all of it or none.** Half of it is worse than either scheme left intact:
- R3 alone routes entries into `docs/changelog/` while R1 still requires reading a file nothing writes — new entries become invisible at session start.
- R1 alone drops the changelog from required reading with nothing replacing it.
- R6/R6b left alone still run a fold against a directory that no longer exists.
- The layout without the backfill takes 64k of history out of required reading and gives nothing back, in exactly the repos with the most to lose. The folder *is* the reach here — an empty one reaches nothing.
- **The backfill without step 2's verification, or with the originals removed before it passes, is the one genuinely destructive half** — it is also the only part of this migration that can lose something, which is why deletion is gated on a count match and lands in the same commit.

**What the migration does.** It *converts* the changelog rather than freezing it, so price it as a conversion and take it in this order:

1. **Backfill every existing entry into `docs/changelog/`.** One file per entry, content copied **verbatim minus the leading number** — the two-tier lead/detail shape governs new entries, and rewriting hundreds of historical ones is hundreds of chances to change what one claims.
   - **Dates are synthesized, not recovered.** Per-entry git archaeology is fragile: entries added in bulk, edited later, or moved during an archival pass all give the wrong answer, and there are hundreds of chances to be wrong. Compute `span_days = yesterday - first_commit_date` (one git call, not one per entry) and `per_day = ceil(total_entries / span_days)`, then walk entries newest-first, assigning `per_day` to yesterday, the next `per_day` to the day before, and so on. That makes the backfill span the repo's actual life instead of inventing history before it existed — 537 entries over a 140-day span is 4 per day across 135 days. With no git history to read, ask for a start date rather than guessing.
   - **Say what the dates are.** They give correct order and rough vintage. They are **not** real, and an entry that cites a dated `docs/specs/…` path will have a filename date that disagrees with its own text. Step 5's pointer is where that gets recorded, so nobody later reads these dates as evidence. Same-day order is arbitrary and doesn't matter — the window reads the whole day.
   - **Every backfilled file records the number it came from** — a marker line in the body, `<!-- entry 534 -->`. This is not optional: it is the only thing keeping existing `entry N` citations resolving once the numbers leave the filenames and the original files leave the tree, and there are usually hundreds of them, inside the entries as well as outside. `grep -rl 'entry 534' docs/changelog/` becomes the resolution path. A duplicated number resolves to two files, which is honest — the repo really has two.
2. **Verify before deleting anything.** Entry count in the originals (`grep -cE '^[0-9]+\. ' docs/CHANGELOG.md docs/CHANGELOG-archive.md`) must equal the file count produced, and each distinct number must appear in exactly as many marker lines as it had entries. **On any mismatch: stop, report, delete nothing** — keep the originals and leave the folder for inspection.
3. **Remove `docs/CHANGELOG.md` and `docs/CHANGELOG-archive.md` from the working tree**, in the same commit as the backfill, so the conversion is one reviewable diff and one `git revert` away. Nothing is lost: git holds them forever, and `git show <pre-migration-sha>:docs/CHANGELOG.md` retrieves them. No history is rewritten. This is the one place the skill removes a changelog file, and it happens only after step 2 passes and only in a migration the user explicitly picked.
4. **Re-point required reading (R1)** — drop the removed files and write the changelog read **exactly as `templates/CLAUDE-root.md` currently states it**, rather than a summary of it. Restating it here is how the migration comes to emit text R1 itself classifies as Outdated: a bare "newest 10" with no date check is a finding, and a migration that writes one fails this skill's next audit. On a repo this size the grep is the step that matters most — it is what makes 537 backfilled entries reachable at all.
5. **Add the pointer.** Append two lines to the file's *Changelog discipline*: that entries predating the migration carry synthetic dates and an `<!-- entry N -->` marker, and that an `entry N` citation resolves by grepping `docs/changelog/`. Without it the citations are unreachable in practice even though the markers are there, and this is also the only durable home for the mid-flight rule below, since a branch carries its own pre-migration `CLAUDE.md`.
6. **Rewrite *Changelog discipline* (R3)** to the folder convention, and **strip the fold** from R6/R6b.
7. **Write the migration's own changelog entry**, into the folder it just created. One file per change applies to this change too, and it is the only dated, greppable record of the event rather than the rule: how many entries were split, the span the synthetic dates cover, and that they are synthetic. Step 5's `CLAUDE.md` pointer states the standing rule; it does not say what happened or when.


**Delegate the backfill, and price it at the offer.** Reading ~470 KB and emitting hundreds of slugged files is the expensive step by an order of magnitude — fan it out over entry ranges, never run it inline in the audit session. Tell the user what it costs (roughly two sessions' worth of the old required read, paid once) **and that the dates it produces are synthetic**. A user who declines keeps the single file; that is a supported state, not a failure.

Note this migration **does** create `docs/changelog/` — it has hundreds of files to put in it. "The first entry creates it" applies only to a fresh scaffold.

**The mid-flight cases.** A branch holding an unfolded `docs/changelog.d/<slug>.md` when the convention changes lands it with `git mv docs/changelog.d/<slug>.md docs/changelog/YYYY-MM-DD-<slug>.md`, dated the landing day — a **real** date, since it is a real landing — and does **not** fold. The fragment was already an unnumbered entry body in a per-change file, so this is a rename, not a conversion, and it needs no number marker because it never had a number. `docs/changelog.d/` disappears with its last fragment, and a fragment holding several entries splits into one file per entry. A fragment already **stranded on `main`** is what the deleted janitor rule existed to catch, so the migration sweeps for it: check `main` for `docs/changelog.d/` and rename anything found into the folder, dated that day, because nothing will ever look there again. And a branch that wrote a *numbered* entry straight into `docs/CHANGELOG.md` under the retired convention needs no special handling: that file no longer exists on `main`, so the merge deletes it and the branch's entry carries over as its own dated file with its number recorded, like any backfilled one.

### R4 — Nested guidance pointers
Lists each subtree `CLAUDE.md` with a one-line scope.
- *Why:* routes the agent to the scoped rules for whatever it's touching.
- *Stale looks like:* a pointer to a subtree that no longer exists, or a missing pointer for a subtree that now has its own `CLAUDE.md`. (Cross-check against the subtrees identified earlier in the run.)

### R5 — Review at commit time (one review point)
The repo has **exactly one review point: the commit** — no per-edit review pass, and no end-of-turn nudge to go run one. When the user asks to commit (or commit and push) and the working tree holds non-trivial changes, the agent **asks first** (`AskUserQuestion`), with **three** options in this order: **`/code-review high --fix`** (the deep pass), **`/fix-code --fix`** (the tight pass), or **commit as-is**. The agent performs the pass; the user only chooses whether it happens and how deep it goes. Asked once per commit request, skipped for a trivial diff or one a full pass already covered, and applied to delegated commits too (`/git commit`) — checked before handing off, since the committing skill never sees the rule. The two review options differ in breadth and cost, and each option is labelled with the path that will actually run: **option 1 is always available as written** — `/code-review` ships with the harness, and the explicit `high` matters because without a level the command reuses whatever level was typed last — and it carries the widest brief (correctness *and* reuse / simplification / efficiency, applied to the working tree). **Option 2 is `/fix-code --fix` when that skill is installed** — consequence-rated 1–5, each finding independently refuted before repair, restore point and `--undo`, and only the serious and unambiguous repaired — and **when it isn't installed, option 2 becomes the agent's own inline pass** over the working diff, scaled to it: one careful read for a small diff; for a substantial or complex one (what an accumulated working tree usually is) a **fan-out across subagents (the Agent tool — no ultracode opt-in needed) one per at-risk dimension (~2–4), each finding verified before it's acted on** (finders on the strong model, verification a tier down — see R7). That inline pass checks correctness, security & data-integrity, edge cases & tests, reuse, clarity, performance, and conformance to the repo's own conventions; applies **every** fix automatically; and reports grouped by severity (blocker / should-fix / nit), one line per bucket, without stopping to ask which to fix. Every path closes by stating plainly anything the review couldn't settle. Also present: the explicit carve-out that **per-change verification is not deferred** — tests, build, and the subtree's own verification workflow still run per change; only the review waits for the commit.
- *Why:* one review of the accumulated diff, at the moment it's sealed into history, is where a review has the most to see and the least to re-litigate. A pass per prompt is mostly waste: it only ever sees its own turn's edits, reviews them from inside the context that just wrote them, and the next follow-up re-opens what it looked at.
- *The pass's rigor is the project's call* — different line counts or a different risk-surface list are both fine. Only the structural drifts below are findings.
- *Outdated looks like* (the first is the highest-value find in any file scaffolded before this convention):
  - **a per-edit review mandate** — "after a non-trivial edit, the change gets a review automatically, in the same turn", with the commit gate as an extra on top or absent. That was the previous convention here; the current one collapses the review into the commit gate. Flag it as Outdated, and when the user picks it, replace the per-edit trigger with the gate while keeping the pass description and any project-specific risk list the file added — the *frequency* is what changed, not the review's content;
  - **no commit gate** — nothing stops a commit no review has seen, so the accumulated diff is never read as one change. This is now the substantive gap (a file with the per-edit mandate *and* no gate has effectively no review point at all);
  - **makes an installed skill the *only* review path** — `/fix-code` named with no inline fallback, so the review goes dead in any checkout where that skill isn't installed and the agent emits an apologetic note instead. A **conditional** preference is correct and must **not** be flagged: "`/fix-code --fix` when installed, otherwise review inline" is right as far as it goes. Note the older gate was itself *gated on* `fix-code` being installed ("without it, commit as asked") — that's this drift too: offer the inline fallback at the gate;
  - **offers only one review option** — a binary *review / commit now* gate, however the review path is spelled. The current convention puts **two** review options in front of the user, deep first: `/code-review high --fix`, then `/fix-code --fix` (inline when that skill is missing), then commit as-is. A file with a working single-option gate is Outdated in the mild sense — add the deep option and the ordering rationale, keep whatever pass description the file already carries;
  - describes the pass as a **cursory single glance** with no subagent fan-out / finding-verification even for a large accumulated diff — the intent is review quality, not a token read;
  - tells the agent to **ask the user which findings to fix** instead of auto-fixing all of them;
  - **routes the user to a separate review pass** — an end-of-turn nudge to run some review command, gated on soft adjectives or hardcoded to one level. Fired on nearly every turn it is pure noise the user learns to skip. The **commit gate** is the one sanctioned stop-and-ask and must **not** be flagged as this drift: it fires only on an explicit commit request (discrete and infrequent, not per turn), and the agent runs the pass itself rather than routing the user elsewhere. Its fixed `high` is not the "hardcoded to one level" drift either — the level is pinned there precisely because `/code-review` otherwise inherits the last one typed;
  - **defers verification along with the review** — the file reads as though tests / build / browser checks also wait for the commit. Only the review does; flag a file that dropped that carve-out.

### R6 — Git workflow: where commits land
States how the agent should use version control here — one of **two** modes: commit directly to `main`, or branch and open a PR per change (with branch-naming / protected-`main` notes) — plus a note that the mode chooses *where* commits go, not *when*. Worktrees are **not** a third mode; they are a separate, additive question assessed under R6b. Where the mode is Branch+PR it also states that the changelog needs **nothing special at landing**: the entry file is written on the branch with its change and rides the PR, no other PR can touch that path, and so nothing about it goes stale however long the PR stays open. The absence of a step is worth stating explicitly — an agent carrying generic expectations will otherwise look for one.
- *Why:* the agent's generic default ("branch first, commit only when asked") may not match this repo; an explicit convention removes the guesswork on every change.
- *Missing looks like:* no git-workflow guidance at all, so the agent falls back to its default. Note: filling this in **requires asking the user** — the choice can't be inferred from the repo.
- *Outdated looks like:*
  - **Branch+PR still describing a changelog fold or fragment** at landing. This is **not a finding of its own** — it is part of R3's migration, which spans R3, R1 and this section together. Cross-reference it there and offer them as one item; raising it here separately is how a repo ends up half-migrated. Check it **here** as well as under R6b, though: a Branch+PR repo that answers "no" to the worktree question never reaches R6b at all, so this is the only place its landing sequence gets looked at;
  - **Branch+PR that says nothing about the changelog at landing** on a repo already on the folder convention — a mild find. The entry needs no step, but an agent that isn't told so will invent one or go looking for a fold that doesn't exist;
  - a "Direct to `main`" section that says to commit when a change is "complete" without stating that committing is still user-initiated — the agent reads it as license to commit proactively the moment work is done. Flag it and add the "where, not when" clarification;

### R6b — Git workflow: the worktree subsection
Separate from R6 and **additive to it**: whether the file carries a *Working in a worktree* subsection describing how a session behaves while it is inside a git worktree — short-lived local `wt/<slug>` branches, where worktrees live, the changelog's base-copy caveat, the landing sequence, and the keep-or-remove question. It composes with **either** answer to R6: a repo can commit straight to `main` *and* sometimes move a piece of work into a worktree, and then it wants both behaviours, selected per session by where the session actually is.
- *Why:* this is the item most likely to be silently missed on an existing file, and it was structurally impossible to catch before: worktrees used to be modelled as a *third mode* alongside the other two, so a file that had already picked "Direct to `main`" satisfied the git-workflow item and the worktree guidance was never offered. Absence of a worktree subsection therefore proves nothing about whether the repo uses worktrees.
- **You cannot infer this one — you must ask.** For any file whose R6 mode is present and current but which has no worktree subsection, ask the user whether work in this repo is ever isolated in a git worktree, exactly as the initial scaffold's question (b) does. Do **not** classify it OK on the grounds that the mode is filled in, and do **not** classify it Missing on the assumption that every repo wants worktrees. Ask, then: *yes* makes it a **Missing** finding (add the subsection); *no* is not a finding at all. Nothing in R3 has to change either way — the changelog convention is mode-independent, so the answer to this question no longer has a changelog consequence, which it did under the retired fragment scheme.
- *Outdated looks like:* a worktree section that exists but is written as a **mutually exclusive mode** — "keep the one mode that matches this repo, delete the others", worktrees presented as an alternative to committing on `main` rather than as an overlay on it. That framing is what makes a repo pick one and lose the other, and it also leaves the agent no rule for deciding which applies in a given session. The fix restructures it as a subsection and adds the **detection** rule: where you are is a fact to check, not a setting to remember — `git rev-parse --path-format=absolute --git-dir --git-common-dir` prints two identical paths in the main checkout and two different ones in a linked worktree, and the first line of `git worktree list` is the main worktree. Flag a detection rule that omits `--path-format=absolute` — without it the two paths differ whenever the session is in a *subdirectory* of the main checkout, so every monorepo session below the root is misclassified as being in a worktree. Also flag a worktree section that assumes direct-to-`main` landing when the repo's R6 mode is Branch+PR (there the worktree's branch *is* the PR branch and is pushed, rather than fast-forwarded into `main` locally). Beyond that:
  - a worktree subsection whose prohibition lands on **creating branches** rather than on **pushing** them and opening PRs. A worktree is normally backed by a local branch, so "no feature branches" forbids the mechanism the mode depends on instead of the thing actually ruled out (a branch reaching `origin`, a PR flow). Reword to "never push any branch but `main`" and keep the delete-at-landing rule;
  - a worktree subsection that doesn't say where the review gate fires. It fires at the **worktree's commit** — with `main` merged in and conflicts resolved *before* that commit, so the resolution is inside the reviewed diff — and the merge into `main` afterwards is mechanical and gets no second pass. A file that leaves this open either loses the gate entirely (the commit happens in the worktree, where nothing invoked it) or pays for two passes over one change;
  - a worktree subsection that states the policy but not the **landing mechanics**, leaving the agent to discover them by hitting refusals: `main` can't be updated from inside a worktree (`git push . HEAD:main` and `git branch -f main` are both rejected while `main` is checked out elsewhere — drive the main checkout with `git -C` instead), a branch can't be deleted while its worktree exists, `rm -rf` on the worktree leaves it registered until `git worktree prune`, and `git worktree remove` run from inside the worktree deletes the agent's own working directory. Where the session uses `EnterWorktree`, add that landing must precede `ExitWorktree` — its `remove` refuses on unlanded commits, and the escape hatch (`discard_changes`) destroys the work;
  - a worktree subsection or Branch+PR mode that still **folds a changelog fragment** at landing, or requires **`git merge --no-commit main`** so the fold rides inside one commit. Both belong to the retired staging area: with a per-entry folder there is nothing to fold, and the flag's only justification was keeping the fold in the same commit as the merge. Plain `git merge main` is now correct — a clean merge commits itself and that merge commit carries no authored content, while a conflicted one leaves the resolution uncommitted, which is what keeps a hand-resolved merge inside a reviewed commit without any flag. Route this to R3's migration; it is not a separate finding. Conversely, flag a landing sequence that says a clean merge needs no review **without scoping that to the clean case** — read unscoped it licenses landing a hand-resolved merge unreviewed, which is the one thing the review-gate placement above exists to prevent;
  - a worktree subsection that **decides the worktree's fate silently** — tearing it down, or leaving it, without asking — or that asks in a *second* prompt after the review gate. Landing is the one moment the choice is decidable, so it belongs in the same `AskUserQuestion` as the review question, with keep as the default and removal withheld while anything in the worktree isn't landed. Also flag wording that makes *any* landed branch drift: after a fast-forward the branch equals `main` and continuing to work on it is normal — drift is a landed branch nobody is working in. And flag a mode that doesn't say **what counts as a landing** ("commit and push" can only mean `main` here, so it lands; a bare "commit" is a checkpoint);
  - a worktree subsection that doesn't distinguish **feature** worktrees from the ephemeral ones a fan-out creates (R7). Fan-out worktrees don't commit; their edits land in the parent tree and pass one gate there. Without the distinction, a fan-out fragments the accumulated diff into per-slice reviews — the exact thing R5's single gate exists to prevent.

### R7 — Multi-agent workflow (ultracode) cost-tiering
When the agent fans a task across subagents (the Workflow tool / "ultracode"), it tiers model + reasoning effort per agent — strongest model for contracts / correctness-critical implementation / adversarial review; a mid model for build-test runners, mechanical implementation, verifying concrete already-stated findings, and applying decided fixes; the cheapest model + low effort for docs / i18n / styling — with the guardrail that the *catching* stage (review) stays strong while *checking* stages (verification) drop a tier unless the finding is subtle or sits in a file whose own risk is security-/data-integrity-critical (judged per file, not by classifying the whole diff — a large commit is usually mixed). It also covers **invoking a named/pre-built workflow**: those carry no model overrides of their own, so every stage inherits the session model and the fan-out has to be sized before launching rather than retiered after. And it ties back to R5: **a workflow's aggregate diff is what the commit gate is for** — no single subagent saw the whole combined change, and a review stage inside the workflow only checked its own findings, so the landed diff gets the substantial-diff treatment at the gate rather than an extra pass on return.
- *Why:* an untiered fan-out defaults every agent to the session's strongest (most expensive) model; tiering cuts cost without touching the stages that catch problems. Verification checks a finding the review already caught, so it doesn't need the strong tier by default. And a named workflow you merely *invoke* silently bills all its stages at the top tier — the trap that only-authoring guidance misses.
- *This is a suggestion, not a hard gap.* Only offer it for a repo where multi-agent workflows are plausibly used; a tiny library that will never run one doesn't need it. Absence is not a finding on its own.
- *Outdated looks like:* R7 is present but (a) covers only *authoring* (setting `model` per `agent()` call) and omits the **named/invoked-workflow** case — that invoking a pre-built workflow runs all its stages on the session model unless its script is edited to tier the checking stages down; or (b) omits the **aggregate-diff** tie-back — that a fan-out's landed diff is nobody's reviewed work and so is the clearest case for *review first* at the R5 gate. Flag either missing piece as Outdated (only where R7 is otherwise warranted); (b) is minor. A file that instead mandates a **self-review the moment a workflow returns** is carrying the older convention — same finding as the per-edit mandate in R5, fold it into that one.

### R8 — Owed follow-ups (`docs/CLAUDE_TODO.md`)
An *Owed follow-ups* section describing a single mutable list of work the project owes and hasn't done, written and drained by the agent: **not a work queue** (an item is never a reason to start work — it is surfaced when the user asks for a change in that area, and the user decides whether it comes into scope); a line earned only by something genuinely owed, found incidentally, and out of scope for the change in hand — not ideas, not refactor wishes, not anything cheaper to fix than to record; a one-bullet shape carrying what is owed, why it matters, and the changelog slug that surfaced it, under a fixed in-file note for whoever opens the file without having read `CLAUDE.md`, and with no further structure — no grouping, priorities, owners, dates, status, done section or item numbers; the **user-facing handles**, since writing the list is the agent's and acting on it is the user's — show what's outstanding, do a named item, *drop* one without doing it (the one deletion that isn't a completion and earns no entry), add one on request — plus saying in the turn when a line was added; **deletion on completion**, in the same change that does the work; the pairing rule that a deferred follow-up is written *both* here and in its entry's `## Detail` (satisfied whichever of the two sections states it); that nothing ever cites the file; and that it stays one file. **Two halves**, like R1 and R3: the section, plus the read in the required-reading block — stated as an **action**, not `@docs/CLAUDE_TODO.md`, since the file doesn't exist until the first item is written. Both halves are judged here, so R1 stays about the changelog.
- *Why:* an append-only changelog cannot say what is *still* outstanding. A deferred follow-up recorded in an entry's `## Detail` is a permanent statement about a past change, and it goes on reading as owed long after the work is done, so the only way to know the present state is to re-derive it. This file holds the present tense, and it can only do that because items are deleted — which is also why the entry is written too: the reasoning has to survive the deletion. The read is cheap by construction (a draining list, absent when the project owes nothing), and the ownership rule is what keeps it that way — a list anyone may fill and nobody must drain becomes a backlog, and a backlog at session start is read once and skimmed thereafter.
- **Absence is an ordinary Missing finding** — additive, no user question needed, unlike R6b. It costs a repo nothing until a session has something to write. **Apply its two halves together** — separable from every other finding, not from each other, because either alone is worse than neither: the section without the read is a file written every week and loaded never, and the read without the section loads a file the session has no rules for writing to. Don't offer them as two picks. And **create no `docs/CLAUDE_TODO.md` while applying it** — step 7's don't-create rule is not fresh-scaffold-only here. The audit adds the convention; the repo's first real deferral is what creates the file, and an empty one dropped in alongside the section is the same inverted-ownership mistake step 7 describes.
- *Outdated looks like:* **framed as a queue the agent works from** ("pick up items from `CLAUDE_TODO.md`", "start each session by clearing outstanding items") — the highest-value find here, because that version manufactures unrequested work out of a file the agent also writes, and the loop closes with nobody having asked for anything; **a done / completed section, `[x]` checkboxes, or struck-through items** — the list stops draining, duplicates the changelog, and every read now costs the history too; **a user-inbox framing** ("add tasks here for Claude") — a second, weaker request channel competing with chat, which goes stale precisely because the user has a better one; **items with no origin slug**, so the reasoning behind a line is gone the moment its session ends; **priorities, dates, owners, nesting, or status fields** — ceremony on a list whose whole value is being cheap to read and cheap to delete from, and the tell is a file with more structure than items; **split into a folder** (`docs/todo/*.md`) mirroring the changelog layout — the opposite lifecycle gets the opposite treatment, since a list you can't see at once isn't a list and per-item paths invite exactly the citations the convention forbids; **no user-facing handles at all** — the section tells the agent to write and drain but never says what the user says to see, do, drop or add an item, so the list is only ever actioned when the agent happens to surface something and pruning isn't a thing the user can ask for; **items appended silently**, with no rule to mention it in the turn, so the file grows where the user isn't looking; **no in-file note**, leaving a bare list in the repo whose only explanation lives in a `CLAUDE.md` that nobody browsing the file is reading; **the discipline present but nothing in required reading** — a file written every week and loaded never; and conversely **`@docs/CLAUDE_TODO.md` in the read-first block** — a dangling load in every repo that currently owes nothing, i.e. the healthy state.
- *Check the disk, not just the text* — `test -f docs/CLAUDE_TODO.md`, once per audit, the same way R1 checks for a digest. A file present with no section in any `CLAUDE.md` is the orphan case: it is being appended to and read by nothing. **Don't adopt its contents.** Predating the convention, its items were written by a person and are therefore requests, not the agent's own deferrals — so add the section (Missing), then list the existing items back to the user and ask what to do with them. Converting them silently into agent-owned lines claims a provenance they don't have, and deleting one on the grounds that the convention says done items go is the same error in the other direction.

## Subtree `CLAUDE.md` rubric

Source of truth: `templates/CLAUDE-subtree.md`. Apply per subtree file.

### S1 — Scope + contents
A one-line description of what lives in the subtree, plus a contents list.
- *Why:* orients the agent before it touches the subtree.
- *Stale looks like:* unfilled `<placeholder>` text.

### S2 — Required tools
At minimum the `LSP` for the subtree's primary language; browser tools (Playwright MCP) for UI subtrees; load instructions quoted if the tool is deferred.
- *Why:* the agent needs the right tools loaded to work effectively here.
- *Outdated looks like:* no LSP entry; a UI subtree with no browser-automation tool.

### S3 — Testing
The actual test framework named and pinned (Vitest / Jest / xUnit / pytest / …), plus the forcing rule: *do not introduce a different test framework without updating the architecture doc.*
- *Why:* stops the agent from silently fragmenting the test stack.
- *Outdated looks like:* a framework named but the forcing rule dropped; a generic unfilled placeholder where the framework should be.

### S4 — Verification workflow (UI subtrees only)
For UI subtrees, the numbered Playwright-MCP pattern: start dev server → drive the changed feature in a real browser → check console + network for errors → only then report complete.
- *Why:* a passing `tsc`/unit suite doesn't prove a UI change actually works.
- *Missing looks like:* a UI subtree with no browser-driven verification step. (Backend/library subtrees don't need this — don't flag its absence there.)

### S5 — Required skills
Project-specific skill mandates (a design system, security review, naming conventions, …).
- *Why:* chains the agent into project-specific discipline.
- *Note:* this is genuinely optional — **zero required skills is a valid choice**, so absence is **not** a finding on its own. Only flag it if there's an obvious installed, clearly-relevant skill the subtree should be mandating (e.g. a `*-design-system` skill for a frontend subtree) — and even then, frame it as a suggestion, not a gap.

## Applying updates (surgical / additive)

When the user picks a file to update, apply only its findings, and preserve everything else:

- **Missing** → add the section, filled from the project the same way a fresh scaffold would (read the manifest / architecture doc for the real values; don't paste raw placeholders).
- **Outdated** → rewrite that section to the current recommendation's intent, but keep any project-specific wording wrapped around it. Don't reword satisfied parts just to match the template. **One carve-out:** where R3's migration rubric classified the repo's changelog *layout* OK, an orthogonal R3 fix (brevity framing, state-delta framing) is applied inside the file's existing single-file convention — its numbering, append-to-the-end and archive wording stay verbatim. "The current recommendation's intent" here means the entry-quality intent, not the layout.
- **Stale** → fix it (update the pointer, fill the placeholder) or, for a deleted-subtree pointer, remove that one line.
- **Never delete** custom sections the template never had — forcing rules, naming conventions, deployment notes. They're the whole reason the update is surgical and not a regeneration.
- Always **show the diff and confirm** before writing. A file the user didn't pick is left exactly as-is.
